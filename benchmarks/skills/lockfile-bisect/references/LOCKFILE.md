# Lockfile regeneration reference

Iris uses [conda-lock](https://github.com/conda/conda-lock) to generate
fully-pinned `@EXPLICIT` lockfiles from the YAML spec files in
`requirements/`.

## Files

| File | Purpose |
|------|---------|
| `requirements/py312.yml` | Conda environment spec for Python 3.12 |
| `requirements/py313.yml` | Conda environment spec for Python 3.13 |
| `requirements/py314.yml` | Conda environment spec for Python 3.14 |
| `requirements/locks/pyXYZ-linux-64.lock` | Pinned lockfile for linux-64 |

## Primary method — `make lockfiles`

Requires conda-lock to be installed in the active environment.

```bash
# From the repo root
make lockfiles
```

This runs:
```bash
python tools/update_lockfiles.py -o requirements/locks requirements/py*.yml
```

conda-lock can be unreliable (resolver timeouts, unexpected errors). If it
fails, use the fallback method below.

## Fallback method — `conda env create` + `conda list --explicit`

This creates a temporary environment directly from the YAML spec and exports
the explicit package list. Repeat for each Python version.

```bash
# Python 3.13 example
conda env create -f requirements/py313.yml --name tmp-bisect-env --yes
conda run -n tmp-bisect-env conda list --explicit \
    > requirements/locks/py313-linux-64.lock
conda env remove --name tmp-bisect-env --yes
```

> **Note:** The header lines generated by `conda list --explicit` use a
> slightly different format from conda-lock output. They should still work
> with `conda create --file`, but the file will start with `# This file may be
> used to create an environment with: # $ conda create --name <env> --file
> <this file>` rather than the conda-lock header comment.

## UK Met Office users — normalising URL prefixes (ssstack)

UK Met Office machines use an internal conda-forge mirror. The URL prefix in the
generated lockfile will differ from the standard `https://conda.anaconda.org/`
prefix. This means:

- Committing the raw lockfile will break CI (CI uses standard conda-forge).
- A direct `diff` with the original lockfile is misleading.

Use `ssstack shareable` to replace internal URLs with standard ones:

```bash
ssstack shareable requirements/locks/py313-linux-64.lock \
    > requirements/locks/py313-linux-64.lock.tmp
mv requirements/locks/py313-linux-64.lock.tmp \
    requirements/locks/py313-linux-64.lock
```

Repeat for all lockfiles that were regenerated. After this step, the lockfile
can be committed and will function correctly with CI.

Ask for help if `ssstack` is not on `PATH`.

## Verifying the output

After regeneration, check:

1. The pinned package is at the expected (old) version:
   ```bash
   grep "numpy" requirements/locks/py313-linux-64.lock
   ```

2. The diff is not unexpectedly large:
   ```bash
   git diff --stat requirements/locks/
   ```
   A bisect pin for a single package typically changes only a handful of lines.
   A diff touching >50 packages suggests a solver cascade — confirm with the
   user before committing.

## Pinning syntax in YAML specs

To pin a package below specific version, use the less-than constraint. Avoid `==` pins, 
as these can cause problems during solving.

```yaml
# Example: rolling back numpy
- numpy <2.1.3
```

To remove a pin, recover the previous line using the Git history, to avoid accidentally
broadening or breaking the spec.
